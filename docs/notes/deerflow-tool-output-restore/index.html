Agent Runtime · 会话恢复

Agent 恢复会话后，为什么读不到工具结果？

工具结果首次写出能读，但会话恢复后，挂载沙箱可能拿不到同一个文件。

PR 合并于 2026-10-25 19:22（北京时间）上游 PR ↗发布版本 ↗
我的贡献
让恢复路径遵循首次写入的文件权限策略，同时保留原子发布和异常清理。
验证
旧版 4 个权限用例失败；修复后 8 组相关套件共 505 项通过。

对 Agent 来说，恢复会话不只是把消息历史接回来。工具消息里引用的文件也要继续可读。DeerFlow 在启用 blob 存储后，会从 blob 恢复被外置的工具结果；即使文件内容恢复正确，文件权限仍可能变掉。

问题出在两条写入路径

在常见的 POSIX 环境里，进程的 umask 022 会让普通文件以 0644 创建。但旧恢复路径用固定为 0600 的临时文件，换一个 Gateway 恢复后，文件内容不变，读取权限却变了。由不同用户身份运行的挂载沙箱因此可能读不到结果。

我的修改：让恢复与首次写入遵循同一策略

在目标路径旁独占创建临时文件，让系统按恢复端的普通创建策略应用权限；写入后同步文件内容，再原子替换目标。失败时只清理自己创建的临时文件。若本地文件已有匹配的内容摘要，仍直接复用。这里没有用统一 chmod 644，所以更严格的 umask 077 仍可生效。

如何验证，哪些不在结论里

上游 PR 记录了使用真实中间件和本地文件系统 blob store 的回归。旧版在 022、002 下的同步和异步恢复共四项失败，077 对照组仍正常；修复后八组相关套件共 505 项通过。另覆盖临时文件冲突和发布失败后的清理。

这里直接验证的是 POSIX 文件权限，不把它写成真实跨 UID 沙箱端到端通过；Windows 和网络文件系统也未覆盖。恢复沿用本机默认 ACL，不保留被替换文件原有的手工权限和额外属性。这项修复已合入，包含于 v2.2.0。PR 中有 Codex 协助。
